## Problem Statement

Email is the most exploited attack vector for phishing, business email compromise (BEC),
and financial fraud — yet existing tools only give per-email verdicts. Forensic investigators
need to know not just "this email is phishing" but "this email is part of a campaign
targeting 12 organizations from the same bulletproof hosting provider."

SIH problem PS 26106 asks for a platform that: detects fraudulent emails using NLP/ML,
analyzes headers and relay paths, geolocates originating IPs, correlates related emails
into campaigns, and generates forensic reports suitable for institutional and law
enforcement use.

## What Makes This Cool

The one-click forensic report. Paste a raw .eml file, click Analyze — 30 seconds later
a downloadable PDF appears with: fraud verdict, relay trace, geolocation map, WHOIS
data, and indicators of compromise. No other competing SIH team (4 found on GitHub)
is doing campaign correlation — every existing tool treats each email in isolation.
The campaign clustering view is the differentiator that turns this from "a better
MXToolbox" into a forensic intelligence platform.

## Approaches Considered

### Approach A: Single-File Analyzer (rejected)
Stateless Next.js app, no database. Ships fast (5–7 days) but no campaign correlation.
Rejected because it produces a scanner, not a forensic intelligence platform.

### Approach B: Browser-Only Privacy-First Lab (rejected)
All processing in-browser via transformers.js. No persistence = no campaign correlation.
Also: 50MB first-load kills the live demo. Rejected.

## Recommended Approach: Full Platform with Campaign Intelligence

**Stack (Next.js-only — scope reduction: FastAPI dropped at eng review):**
- Runtime: Next.js 14 (App Router) + Tailwind + shadcn/ui — frontend + all API routes
- Database: PostgreSQL via Supabase (free tier) + Prisma ORM
- Email parsing: `mailparser` npm — header extraction, relay hops, `Authentication-Results`
- ML: HuggingFace Inference API — `facebook/bart-large-mnli` zero-shot, called via `fetch`
  from Next.js API route. Labels `["phishing", "legitimate"]` → 0–1 confidence score.
- Geolocation: ipinfo.io free tier (50k requests/month) — `fetch` from API route
- IP reputation: AbuseIPDB free tier (1k requests/day) — `fetch` from API route
- WHOIS: `whoiser` npm (pure JS, no system binary dependency)
- URL extraction: regex in Next.js API route
- SPF/DKIM/DMARC: parse `Authentication-Results` header from .eml via mailparser —
  no cryptographic re-verification; no DNS lookup needed for demo
- PDF: `@react-pdf/renderer` — React-based PDF generation, runs in Node.js API route
- Map (PDF): formatted IP hop table (country, ASN, org per hop) — no external map API
- Map (UI): Leaflet.js — stretch goal only; relay hop table is the baseline

**Architecture (2 services — Vercel + Supabase):**

```
[Browser] → [Next.js on Vercel]
              ├── /app (React UI)
              └── /api routes
                    ├── POST /api/analyze  ← SSE stream (bypasses Vercel 10s limit)
                    ├── GET  /api/campaigns
                    └── GET  /api/report/[id]  ← PDF download
                          ↓
                   [Supabase PostgreSQL]
                   [HuggingFace API]
                   [ipinfo.io API]
                   [AbuseIPDB API]
```

`POST /api/analyze` returns a `ReadableStream` using Server-Sent Events. Each pipeline
step emits a `data:` event as it completes. The browser renders live progress:
`Parsing headers... ✓ → Geolocating IPs... ✓ → Classifying content... ✓ → Done`.
This bypasses Vercel Hobby's 10-second function timeout — streaming responses are not
subject to the execution limit in the same way as synchronous responses.

**Core data flow:**

1. User pastes .eml text or uploads .eml file → POST /api/analyze (SSE stream opens)
1a. Input validation: reject if > 500KB (base64 attachments can balloon to 10MB); attempt
    to parse with `mailparser`; if `from` or `messageId` missing, emit error event and
    close stream with HTTP 422 message.
2. `mailparser` parses headers: all `Received` hops, originating IPs, `Authentication-Results`
   → emit `{"step":"headers","status":"done"}`
3. All relay IPs → `Promise.all(ips.map(ip => fetch(ipinfo.io/ip)))` (parallel, not sequential)
   → emit `{"step":"geolocation","status":"done","hops":N}`
4. Email body + subject → `fetch` HuggingFace Inference API (phishing classification score)
4a. URL extraction from body via JS regex → stored in `email_urls` table
   → emit `{"step":"classification","status":"done","score":0.87}`
5. Sender domain → check `email_domains` DB cache first (7-day TTL by domain) — if cached,
   use stored whois_age_days + registrar; if not, `whoiser` npm lookup → store result.
   Caching prevents WHOIS rate-limit on repeat sender domains.
   → emit `{"step":"whois","status":"done"}`
6. AbuseIPDB check on originating IP ONLY (first non-private Received hop) — checking all
   hops burns through 1k/day budget. Check DB cache first (TTL: 7 days) — if cached,
   use stored score; if not, `fetch` AbuseIPDB API → store in `email_ips.abuse_score`
   → emit `{"step":"reputation","status":"done"}`
7. Fraud score computed (0–100). Verdicts: < 40 = Legitimate, 40–59 = Suspicious, ≥ 60 = Fraudulent.
   - SPF fail: +20 pts | DKIM fail: +20 pts | DMARC fail: +15 pts
   - Sender domain < 30 days old: +20 pts
   - Phishing classifier confidence > 0.7: +15 pts (flat, threshold-based)
   - AbuseIPDB score > 50: +10 pts
   - Cap at 100. If SPF + DKIM + DMARC all fail simultaneously: minimum verdict = Suspicious
     (score floor set to 40) regardless of other inputs.
8. Result stored in PostgreSQL (email hash, fraud score, IPs, domains, indicators)
9. Campaign clustering: on every new email, query DB for emails sharing ≥1 IP or
   sender domain → union-find on shared IPs/domains, run on every insert
   → emit `{"step":"complete","emailId":"<uuid>","verdict":"Fraudulent","score":82}`
   → stream closes
10. PDF report generated via `@react-pdf/renderer` in Node.js → returned as download
    from GET /api/report/[id] (separate synchronous route, PDF fits within 10s)

**Campaign clustering (the differentiator):**

DB schema (minimal):
```sql
emails(id, hash, subject, sender, fraud_score, verdict, analyzed_at, raw_eml TEXT)
email_ips(email_id, ip, country, asn, abuse_score)
email_domains(email_id, domain, whois_age_days, registrar)
email_urls(email_id, url)  -- extracted from body via regex
campaigns(id, created_at)  -- email_count derived via COUNT, not stored
email_campaigns(email_id, campaign_id)
```

Note on auth: no authentication for demo — any visitor can view all analyzed emails.
Acknowledged: demo only, not for production forensic use.

Algorithm: union-find on shared IPs and domains, run synchronously inside the same DB
transaction as the email insert. When a new email shares an IP or domain with existing
emails in different campaigns, merge those campaigns — lowest ID wins, all
`email_campaigns` rows updated to the surviving ID in the same transaction.
Known limitation: concurrent inserts can race on campaign IDs. Acceptable for demo
(low concurrent traffic); use a DB-level advisory lock if this causes issues.
Display: "Campaign #4 — 7 emails, originating from AS-47764 (HostKey Russia)."
("target orgs" removed — not in schema; derive later from To: headers if time allows.)

**PDF report sections:**
1. Executive Summary (verdict + confidence score)
2. Email Header Analysis (relay hops, anomalies flagged)
3. Authentication Status (SPF/DKIM/DMARC results)
4. Geolocation Trace (map image + table of hop IPs with country/ASN/org)
5. Domain Intelligence (WHOIS for sender domain)
6. NLP Phishing Analysis (BART zero-shot confidence score for "phishing" label;
   no phrase extraction — classifier returns scores, not spans)
7. Campaign Attribution (optional — omitted with placeholder text if no campaign match found)
8. Indicators of Compromise (IPs, domains, URLs extracted)

## Open Questions

- HuggingFace Inference API latency: free tier can be slow (~10s on cold start).
  Mitigation: show a progress bar; add HuggingFace dummy inference call to the same
  GitHub Actions keep-alive cron that pings Supabase and Render (every 10 minutes
  during the 48h demo window). Pre-warming on app start does not survive Render
  spin-down and is NOT used.
- ipinfo.io free tier: 50k requests/month. At ~5 IPs per email, covers ~10k emails.
  Fine for demo.
- AbuseIPDB free tier: 1k requests/day. At 1 per email analysis, covers 1k emails/day.
  Fine for demo. Cache results in the DB to avoid re-querying the same IP.
- Supabase free tier pauses after 1 week of inactivity. Mitigation: GitHub Actions cron
  (`0 */72 * * *` — every 3 days) hits the `/health` endpoint to keep it alive.
- Vercel Hobby 10-second function timeout: mitigated by SSE streaming on POST /api/analyze.
  PDF generation (GET /api/report/[id]) is synchronous and must complete under 10s —
  @react-pdf/renderer on a pre-fetched result set is fast enough; benchmark before shipping.
  Keep-alive cron pings HuggingFace to prevent cold-start latency during the demo window.
- API error behavior: for any external API failure (HuggingFace timeout, ipinfo.io 429,
  AbuseIPDB failure, WHOIS timeout), return a partial result with that signal marked as
  "unavailable" — never block the full analysis on a single service outage.

### Failure Modes

| Failure | User sees | Mitigation |
|---------|-----------|-----------|
| HuggingFace 503 cold start | Classification marked "unavailable"; rest of analysis continues | Keep-alive cron + retry once after 3s |
| ipinfo.io 429 | Affected IP geolocation marked "unavailable" | Partial result — never block full analysis |
| AbuseIPDB failure | Reputation marked "unavailable" | DB cache hit for repeat IPs; partial result on miss |
| WHOIS timeout | Domain age marked "unavailable" | Promise.race with 5s abort |
| DB transaction failure | 500 error, SSE stream closes with error event | Prisma handles rollback; user can retry |
| Browser closes mid-stream | Server continues processing (Node.js streaming is server-side) | No action needed |
| PDF > 10s on Vercel | 504 gateway timeout | Benchmark on Day 10; simplify PDF if needed |
